# OpenMV—STM32 串口收发协议

日期：2026-10-09。适用：上电自动路线中的二维码联调。

**发送可以附带 `\r\n`；接收固定命令时，只识别命令词，不等待回车换行。** OpenMV 收到 `qr` 就进入二维码任务，完成后回复 `finishqr`。本次无需发送 `start`，也无需等待 `finishstart`。

## 1. 接线与发送格式

- STM32 USART3：115200、8N1；PD8（TX）接 OpenMV RX，PD9（RX）接 OpenMV TX，双方共地。
- 命令使用 ASCII 小写字母。固定命令内部不加空格、不加换行、不加参数。
- 命令末尾允许不加结束符，或加实际 CR、LF、CRLF，解析结果相同。
- 文中的 `\r\n` 表示两个控制字节 `0D 0A`，不要把反斜杠、r、反斜杠、n 当作四个普通字符发送。

| 方向 | 命令词 | 可以接收的发送形式 | 含义 |
| --- | --- | --- | --- |
| STM32 → OpenMV | `qr` | `qr`、`qr\r`、`qr\n`、`qr\r\n` | 第一段直行完成，开始二维码任务 |
| OpenMV → STM32 | `finishqr` | `finishqr`、`finishqr\r`、`finishqr\n`、`finishqr\r\n` | 二维码任务成功完成，允许继续路线 |

**当前 STM32 实际发送 `qr\r\n`，四个字节为 `71 72 0D 0A`；其接收程序支持上述四种 `finishqr` 形式，不等待换行。** 2026-10-09 为排查红4随后红7，发送端补上 CRLF，兼容按行接收的现有视觉程序；OpenMV 仍应按下文实现不依赖换行的固定命令解析。OpenMV 推荐这样回复：

```python
uart.write(b"finishqr\r\n")
```

## 2. 当前任务流程

```text
STM32 上电，等待 BMI、底盘反馈和停稳条件
    ↓
第一段前进 800 mm，完成后停车
    ↓
STM32 发送 qr\r\n（当前每次到站只发一次）
    ↓
OpenMV 收到完整 qr，开始二维码识别
    ↓
OpenMV 识别处理成功，发送 finishqr，可附带 \r\n
    ↓
STM32 收到完整 finishqr，继续当前配置的剩余路线
```

OpenMV 应在小车到达第一站前完成串口接收初始化，并持续处理接收数据。当前路线只启用二维码握手；后续路线结束时发送 `0 DONE ROUTE\r\n`，本轮没有启用 `globule/finishglobule` 等待点。

## 3. OpenMV 接收端怎么做

以下是给 OpenMV 同事的接收实现要求，使用现有 UART 和识别程序接入。

1. 主循环读取当前已到达的字节，加入跨循环保留的接收缓冲。不要用“等到换行才交付命令”的 `readline()` 逻辑处理 `qr`。
2. 在命令边界忽略额外的 CR/LF。它们不计入命令长度，也不产生新任务。
3. 从缓冲头识别完整命令词 `qr`。两个字节收齐就消费它们、产生一次二维码请求事件，无需等第三个字节或换行。
4. 只有 `q` 时保留，等后续 `r`；不要因一次 `uart.read()` 只得到半条命令就丢弃。
5. 处理一条消息后继续处理剩余缓冲，支持一次读取包含多条消息；只保留尚未收齐的内容。
6. CR/LF 只允许出现在命令之间。`q\r\nr` 不是合法的 `qr`，不得先删除所有换行再拼成命令。
7. 接收缓冲应有上限，例如 256 字节；调试长行可边收边丢弃至行尾，不要无限累计。

**不要在整段串口文本里直接搜索子串 `qr`。** STM32 同一串口还会输出状态和调试行。以 `#` 或数字开头的行属于调试/状态信息，应按现有 CR/LF 行格式单独处理；不能把这些行内部的文字当作任务命令。即使调试行分多次到达，也要保留“正在接收调试行”的状态。其他未知文本丢弃到行尾，不能从其中截取 `qr`。

这里仅调试/状态文本使用原有行边界；`qr` 的识别不依赖行边界。不要把一次读取的全部内容直接与 `b"qr"` 比较，也不要只对每次读取调用 `.strip()`，这样仍会漏掉拆开的命令或混在状态输出后的命令。

## 4. OpenMV 任务状态怎么做

- 初始进入“等待二维码请求”，持续接收串口。
- 收到 `qr` 后进入“二维码识别中”。识别期间再次收到 `qr`，继续当前任务，不启动第二次识别。
- 识别成功并保存本次需要的结果后，回复一次 `finishqr\r\n`，进入“本轮二维码已完成”。
- 暂时没识别到就继续识别，不能因为“收到请求”或“一次识别尝试结束”就发送 `finishqr`。
- 已完成状态下重复请求不得重新启动本轮任务。重新做整轮测试时，双方应按同一轮次重新初始化任务状态。

STM32 当前不对成功接收 `finishqr` 单独回 ACK；OpenMV 发完后继续处理主循环，不要等待 `DONE` 或周期计数才退出识别任务。`0 DONE ROUTE` 表示整段已配置路线结束。

STM32 最长等待二维码回复 30 秒，超时发送 `0 ERROR VISION_TIMEOUT\r\n` 并停止路线。收到该故障或其他路线故障后，OpenMV 应停止本轮完成回复。超时后补发 `finishqr` 不能恢复路线；重新测试需要双方重新准备本轮任务。

红灯闪4次表示正在等待视觉完成；随后闪7次表示上述30秒等待超时。OpenMV 联调时应在 IDE 终端记录“收到的原始字节及时间、进入识别和识别成功的时间、发送的完成字节及时间/写入长度”，不要将这些调试日志发回底盘控制串口。具体分段定位见 [LED独立上电排查说明.md](LED独立上电排查说明.md)。补换行只解决接收格式兼容，不能证明 OpenMV 已进入识别或已成功回复。

## 5. 给 OpenMV 的验收例子

下表的 `b"..."` 表示字节；同一行用“→”连接的内容表示分多次读取到的数据。

| 接收到的数据 | 预期结果 |
| --- | --- |
| `b"qr"` | 立即产生一次二维码请求，不等换行 |
| `b"qr\r\n"` | 产生一次请求，忽略尾部 CR/LF |
| `b"q"` → `b"r"` | 第一次保留，第二次收齐后产生一次请求 |
| `b"q"` → `b"r\r"` → `b"\n"` | 总共只产生一次请求 |
| `b"\r\nqr\r\n"` | 忽略前后空行，产生一次请求 |
| `b"qrqr\r\n"` | 解析出两条请求，任务状态机只启动一次识别 |
| `b"# action=QR\r\nqr"` | 忽略调试行，只响应末尾真正的请求 |
| `b"finishqr\r\n"` 出现在 OpenMV 接收端 | 不得把其中的 `qr` 误识别为 STM32 请求 |
| `b"q\r\nr"` | 非法拆分，不产生二维码请求 |

## 6. 视觉偏差数据的扩展边界

上面的无结束符识别适用于 `qr/finishqr` 这类固定命令词。此前提出的 `VERR`、`QRDATA`、`VACK`、`VISION_STATUS` 尚未接入当前 STM32 固件。

若后续视觉偏差数据也要求不靠 CR/LF 分帧，协议草案统一采用显式 `<`、`>` 帧边界，例如：

```text
<VERR 1 18.5 -2.4 92 35>\r\n
```

也可以只发送 `<VERR 1 18.5 -2.4 92 35>`。未来接收端从 `<` 缓存到 `>`，收齐后再校验并解析五个字段，忽略帧外可选 CR/LF。最后的 `age_ms` 长度不固定，不能一读到 `3` 就判断它不是 `35`，因此不能直接套用固定命令词的收齐规则。

这部分是后续接入约定，需双方实现后启用；当前二维码联调使用第 1～5 节。视觉字段定义见 [视觉纠偏联调协议.md](视觉纠偏联调协议.md)。
